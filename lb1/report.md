## Висновок

Під час виконання лабораторної роботи було проведено тестування вебзастосунку SauceDemo з використанням різних тестових облікових записів. Базовий сценарій роботи з обліковим записом `standard_user` було виконано успішно.

Під час тестування було виявлено та задокументовано три аномалії, для кожної з яких створено окремий Issue у GitHub із зазначенням умов відтворення, очікуваного та фактичного результату, а також рівнів Severity і Priority.



## Контрольні питання

1.Що розуміють під якістю програмного продукту?

Якість програмного продукту − це сукупність його властивостей, які визначають, наскільки він відповідає встановленим вимогам і потребам користувачів.

2. Чому факт працездатності програми ще не означає її високої якості?

Тому що програма може виконувати основні функції, але мати помилки, незручний інтерфейс, проблеми з продуктивністю, безпекою, надійністю або відповідністю вимогам.

3. Що таке аномалія?

Аномалія −це поведінка або результат роботи програмного продукту, який відрізняється від очікуваного або нормального.

4. Чому аномалія не завжди є дефектом?

Тому що незвична поведінка може бути передбаченою вимогами або особливістю конкретного тестового сценарію. Наприклад, locked_out_user не може увійти в систему, але це очікувана поведінка для заблокованого користувача.

5. Що таке Expected Result та Actual Result?

Expected Result −очікуваний результат, який повинен отримати користувач.
Actual Result — фактичний результат, який було отримано під час тестування.

6. Які три питання використовуються для формування Title, Expected Result та Actual Result у межах курсу?

Що я робив? 
Що очікував? 
Що отримав? 
Вони допомагають сформулювати коротку назву проблеми та чітко розділити очікувану і фактичну поведінку.

7. Для чого потрібен defect report?

Defect report потрібен для документування виявленої проблеми, щоб її можна було зрозуміти, відтворити та виправити.

8. Яку інформацію повинен містити defect report?

Зазвичай він містить опис проблеми, кроки відтворення, Expected Result, Actual Result, тестове середовище, Severity, Priority та докази проблеми.

9. Для чого використовуються GitHub Issues?

GitHub Issues використовуються для створення, опису, обговорення та відстеження проблем і завдань у проєкті.

10. Навіщо до Issue додавати screenshot або відеозапис?

Щоб надати наочне підтвердження проблеми та допомогти іншій людині швидше зрозуміти й відтворити її.

11. Чим Severity відрізняється від Priority?

Severity показує, наскільки серйозно проблема впливає на роботу програмного продукту.
Priority показує, наскільки важливо або терміново виправити цю проблему.

12. Для чого у defect report вказують test environment?

Щоб було зрозуміло, в яких умовах виникла проблема: наприклад, яка операційна система, браузер, версія програми або інше середовище використовувалися під час тестування.
